## D1. TS 迁移与重构的先后顺序

- **背景**：目标是「模块化重构 + 迁移 TS」。两者都是大工程。
- **备选**：
  - (a) 先重构，后 TS
  - (b) 先 TS，后重构
  - (c) 同时进行
- **结论**：**(b) 先 TS（渐进），后重构**。顺序：P1 清死代码 → P2 TS 基建 → P3 渐进迁移 → P4 重构 → P5 收紧。
- **理由**：
  1. TS 是重构的安全网 —— 改接口时编译器 catch 所有调用点。
  2. 迁移是机械的（行为不变），重构是创造性的（故意改结构），必须分开做。
  3. 先删死代码（P1）再迁 TS，避免给注定要删的代码写类型。
- **影响**：全盘路线。
- **日期**：2026-09-18
- **状态**：✅ 已定

## D2. 目录组织：按领域 vs 按技术层

- **背景**：现状按 Electron 的技术层分（`src/main` / `src/preload`），导致功能混淆。
- **备选**：
  - (a) 保留 main/preload，内部细分
  - (b) 改为按业务领域分（app / session / bridge / overlay / tools / providers）
- **结论**：**(b) 按领域分**。
- **理由**：
  1. 现状混淆的根因就是「按技术层分」——`preload/dom/` 里既有桥接逻辑又有 UI。
  2. 领域划分让「一个模块一件事」可落地。
  3. Electron 的 main/preload 边界**已由 `main.js`/`preload.js` 薄壳保留**，不影响打包约定。
- **影响**：全盘目录结构（见 `01-architecture.md`）。
- **日期**：2026-09-18
- **状态**：✅ 已定

- **影响**：命名统一（`New` 后缀）、旧别名删除时机。
- **日期**：2026-09-18

## D7. `tools/` 是否移入 `src/`？

- **背景**：现状 `tools/` 在根目录，与 `src/` 分离。
- **备选**：

## D9. TS 严格度：一步到位 vs 渐进？

- **背景**：13,500 行 JS 迁 TS。
- **备选**：
  - (a) `strict: true` 从一开始
  - (b) `strict: false` + `allowJs`，P5 再收紧
- **结论**：**(b) 渐进**。P2 用 `allowJs + checkJs: false`，P3 迁移时允许 `any`，P5 开 `strict`。
- **理由**：一步到位会导致海量报错，阻塞进度。
- **影响**：P5 需专门一轮「类型收紧」。
- **日期**：2026-09-18
- **状态**：✅ 已定
